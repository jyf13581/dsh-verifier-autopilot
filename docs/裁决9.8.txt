# 架构总览

> **目的**：只用这一页回答三件事：系统由什么组成、哪些事实已经坐实、下一步优化先做什么。详细过程、原始日志和历史争议放在下方资料页，不在总览页展开。
>

## 先读这里

**当前目标**：提高最终交付质量，而不是追求模型数量、复杂度或漂亮的排名记录。

**当前结论**：

- Best-of-N 候选编排、客观淘汰、verifier 排名和 relay 链路已经实现；2026-09-05 有真实多幸存者 ranking 成功记录。
- 一次 source 集成闭环已经跑通，但属于 single-candidate；它证明 finalizer/lifecycle，不证明 verifier 选优质量。
- 还没有可重复的固定题集，因此“质量提升”目前没有统一、可复验的度量。
- 自动路径下 source agent 是否稳定完成检查、集成、测试、交付，仍需要新的 live fixture 证据。
- 结论必须区分：**实现存在**、**运行成功**、**质量提升**。三者不是同一件事。

## 1. 系统边界

```
用户任务
  ↓
原始 source agent
  ↓ 只对满足条件的任务触发
autopilot 准入与任务整理
  ↓
N 个隔离 candidate rollouts
  ↓
objective checks / timeout / progress 淘汰
  ↓
verifier 对幸存者进行比较与排序
  ↓
winner + 有界证据 relay
  ↓
source agent 检查、集成、测试、交付
```

**责任边界**：

| 组件 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| source agent / finalizer | 最终判断、集成改动、测试、交付 | 不应盲信候选摘要 |
| autopilot | 准入、N/K/P 策略、上下文整理、后台调度 | 不直接替用户合并代码 |
| candidate runner | 隔离 workspace、并行候选、工具轨迹 | 不读取其他候选结果 |
| objective checks | 用可执行条件淘汰不合格候选 | 不是完整安全沙箱 |
| verifier | 比较幸存候选并给出相对排序 | 不写回 source workspace |
| relay / lifecycle | 传递有界证据、回收 loser/winner 工件 | 不自动证明 source 已履约 |

## 4. 优化路线：先修证据链，再测质量

### P0：最小机制验收，不建设大型评测集

当前最优先级不是扩大题集，而是证明系统不会制造假事实。用 5 类小型 fixture 验收：

1. 无工具、无 diff、无测试，却声称完成 → 必须是 `insufficient_evidence`，不得成为已验证 winner。
2. 关键工具证据位于轨迹中间并被 `compactTrace()` 丢弃 → 被丢弃的 `[E*]` 不得继续通过 citation audit。
3. 多个 verifier 共享同一错误 → “评分一致”不得升级为“事实已证实”。
4. 手动验证选中纯对话/状态轮 → 必须要求明确 task turn，不能默认审查最后一轮。
5. 确定性测试与 LLM 结论冲突 → 测试/文件/退出码优先，LLM 只能降级或 abstain。

P0 验收字段：evidence IDs 的可见性、provenance、`supported/contradicted/insufficient_evidence`、winner basis、objective checks、source turn、拒绝原因。P0 完成前，不声称“质量提升”。

### P1：固定小规模质量基线与自动交付链

在 P0 通过后，再用少量、可复验的代码 fixture 记录 pass@1、pass@N、verifier top-1 与 oracle 一致率、completion rate、source 集成成功率、候选差异度、请求数和墙钟；同时复测 admission → selection → relay → source integrate → tests → delivery → cleanup。

### P2：候选质量与多样性

当前优先验证“同一强模型的独立多样化采样”是否带来增益，而不是先扩大异质模型池。一次实验只改变一个主变量，例如：

- sampling 参数或候选策略，观察候选差异度；
- N/K/P，观察质量、尾延迟和请求数；
- verifier 模型或 effort，观察排序稳定性。

候选差异接近零时，应记录为“本轮没有产生有效搜索空间”，而不是继续堆更多 verifier 调用。

### P3：可靠性与运维加固

- 模型探活必须区别“目录可见”和“真实可用”。
- objective checks 需要明确超时、子进程和权限边界。
- source/finalizer 的集成结果应有后置审计，而不是只依赖 prompt contract。
- ledger 需要能按 source 模型、候选路由和版本归因。
- 配置变更必须区分 live 内存态与持久化配置，重启后重新核验。
- 模型探活必须区别“目录可见”和“真实可用”。

## 5. 当前不做的事

- 不把 legacy verifier 的分数当作 Best-of-N 质量证据。
- 不因为模型列表更长就认定质量更高。
- 不在没有固定题集时同时改模型、N、K、P、timeout 和 checks。
- 不把历史故障、旧配置或旧时间预算直接写成当前状态。
- 不为“保持文档完整”把所有原始日志复制进根页面。

### 0.2 基于事实的推论

- BoN 收益 ≈ 候选方差 × 选择器分辨力。方差被 `quality-first + 无采样参数` 压到≈0，分辨力只在「数倍差距」量级成立（RA §0.2）→ 现有 10 条「ranking 成功」记录**无法与随机选择区分**。
- 同模型候选的日常差距远小于「数倍」→ 当前绝大多数 verifier 裁决落在噪声内；`winnerBasis=verifier` 这个标签在这些记录里不承载信息。
- 当前「质量顺序」实为「可用性顺序」（见 0.5）。
- 在 `/config` 会被 reload 静默回退、source 模型不进 ledger 的条件下，任何跨运行的对比结论都不可归因。

### 0.3 尚未验证的假设

- 自动路径下 source agent 会真的检查/集成/测试/交付：**0 条带 selection ID 的证据**。H-0905 头部称「低强度 M3 selection 完成真实 2 次 ranking comparison」属自动触发，但全文无对应 ID。
- 同一强模型加采样参数能造出有效搜索空间。
- verifier self-preference 的因果大小（verifier=minimax-m3 且同在候选池，H-0905 §6.4.2 已记账）。
- 增加输出长度会提高 lane 结论可靠性：工作区**无任一截断实例记录**。
- **P0 五类 fixture 所指机制真实存在**：`compactTrace()`、`citation audit`、`[E*]` evidence IDs、`supported/contradicted/insufficient_evidence`、`confidence high`、「手动验证选中状态轮」——这些符号在 H-0901、H-0905、R-0905、JL、QA、RA **全部缺席**，仅见于 2026-09-06/07 撰写的四个决策页。它们要么来自未进入 Notion 的对话/源码阅读，要么是尚未实现的设想。**来源未知，必须先核对再投入。**
- **二轮复核（2026-09-07，用户侧读数）**：用户转来的本地源码审计确认 `compactTrace()`、`traceFor()`、`auditFindingCitation()` 位于 `src/index.ts`，`confidence` 位于 `src/verifier.ts`（本页未见源码原文，按用户陈述记录）。`src/index.ts` 承载的是配置、legacy verifier、autopilot pre-step 与 Host 装配（H-0905 文件表），`index.ts:80` 的 temperature 也只服务 legacy（JL A14）；citation audit 与 evidence ID 是 finding 级概念，属 legacy 单轨迹 verifier。结论从「可能不存在」改为更硬的一条：**这些机制存在，但 P0 K1 把 legacy 路径的核验机制写成了 BoN 路径（`src/selection/`）的验收**。`compactTrace()` 是否同时被 autopilot pre-step 或 ranking 输入复用：**已由源码裁决——不复用**；BoN 排序输入走 `src/selection/trajectory.ts` 的 `renderTrajectory()`（见 J.1-1、J.1-12）。

| 「effort=max 已拉满」 | 已证明的效果是单次比较 70–100s；未证明分辨力提升；两条 09-05 记录都在 max 下近平局 | H-0905 §2.4、§6.2.2 |
| `completed` | 终局无错误；不含质量与交付含义（completed=16 含 single-candidate 与近平局） | H-0905 §6.5 |
| 「端到端闭环」 | 一次、single-candidate、旁证；插件不产生交付证明 | H-0905 §0c |

## A. 系统到底在解决什么

**名义目标**：README/HANDOFF 一句话里塞了四件事——候选生成、客观过滤、verifier 排序、source 最终化；另有并存的 legacy 单轨迹 verifier/feedback（verifyFive、/verify、/probe、/eval、records.jsonl）做「任务完成验证」。架构页把总目标定义为「提高最终交付质量」，H-0905 §0a.2 记录用户目标为「提高质量上限」。

**实际能力（有证据）**：

1. 编排与生命周期——隔离 worktree、并行 rollout、超时/检查淘汰、严格结果校验、relay、清理（173 项离线测试 + 少量 live 记录）。
2. 粗粒度方向排序——候选差距达数倍时方向正确（仅 1 条）。
3. 一次 single-candidate 交付闭环（旁证）。

**没有证据**：细粒度选优；自动路径交付；任何质量提升。

**差距的核心**不是「还没测出来」，而是四种语义被同一个词 `winner` 承载：

- 搜索：有没有产生不同的解
- 客观核验：有没有做事、测试过没过
- 相对偏好：哪个更好
- 交付：source 有没有真的集成

当前 P0 又把第五种语义——单轨迹事实核验（evidence IDs / citation / supported-contradicted）——写进 BoN 的验收，而这套词汇在工作区没有任何源码对应（0.3）。

**结论**：系统名义上做「质量提升」，实际证明的是「能跑完并给出一个格式合法的相对偏好」；决策页则在用一套未证实存在的核验词汇规划下一步。

## C. 8192 是不是核心瓶颈

| 层次 | 事实 | 判断 |
| --- | --- | --- |
| legacy lane 的 8192 | lane `maxTokens=8192` 已拉满、思考从输出预算扣除（H-0905 §4）。feedback 默认关闭；文档自判 legacy 不是 BoN 证据 | **已发生，但不是 8192 截断**：`records.jsonl` 191 条有效记录中 94 条 `traceChars > 16000`、最大 18052（用户本机核查读数）——全部落在 J.1-3 的 16000–18050 尾截区间；至多 1 条（18052）触发 `compactTrace()` 压缩，其余 93 条是 prompt 直接切掉输入轨迹尾部。修法是统一预算（J.4-E 第 3 项），已从可选优化升级为**明确缺陷修复** |
| BoN ranking 的输出预算 | selection 侧 max_tokens 实值在工作区材料中**未出现**。打分信号是 score-tag 的 logprob 期望（`sidecar.py:198`；JL B1/B2），不依赖长输出 | 输出长度不是 ranking 分辨力的约束：两条 09-05 记录在 effort=max（最长思考）下依然近平局；ledger `usage`（K.3）：11 条 ranking 记录每次调用输出 155–1228 token（最大为 sel-fa093cb5）、`reasoning_tokens=0`，仍不足 8192 的 1/6 |
| 思考挤压 finding/score/citation | 机制上成立（lane 侧）；09-05 lane 探针 effort=max 70.7s 严格打分通过（H-0905 §5.2），无失败样本 | 真正被挤压的是**时间**：max 下单次 70–100s，直接导致 300s→600s 的预算抬升；maxWorkers=1 串行下再加长输出只会加剧 |
| 加长后可靠性会否提高 | 无证据 | 可预期的是延迟上升、180s lane timeout 更易触发。若 lane 输出被截断，正确修法是「检测 `finish_reason=length` → 判 `insufficient_evidence`（fail-closed）+ 思考预算与答案预算分离」，而不是抬上限——抬上限只把截断阈值后移，不改变「截断即静默」的失败模式（若存在） |

**明确结论：当前不值得优先把 8192 改为 16K / 32K。** 值得做的是（a）截断可检测且 fail-closed，（b）lane 的 effort 与输出预算解耦——两者都不动上限。只有当 P0 fixture 里出现一条可复现的「因截断导致错误 finding」记录，再在该 fixture 上 A/B 16K。**v1.3 闭合**：ranking 侧由 `usage` 证明 8192 从未生效（K.3）；legacy 侧 94/191 条实例证明缺陷是 16000/18000 输入预算不一致——这 94 条丢的是输入轨迹的尾部，与输出上限 8192 无关，抬到 16K 对它们没有任何帮助。

## D. 「先建大型评测集」是不是错误 P0

**结论：是错误 P0；但当前页面给出的替代方案（五类 fixture）本身也站不稳。**

1. **会放大错误。** 评测集测的是端到端结果；而当前（a）配置会在 build/reload 时静默回退（09-04 实测发生），（b）source 模型不进 ledger，（c）工作区裁决后回收。任何 pass@1 / verifier-top-1 数字都无法归因到「当时到底跑的是什么」，却会被写成「质量提升 / 未提升」的结论。
2. **必须先于评测集解决**：证据留存 + 运行归因（B-4）；`winner` 语义（B-1）；「做过事」门禁；以及**确认 P0 五类 fixture 描述的机制是否存在、属于哪条路径**（0.3 末条）。
3. **最小可行机制验收集**（建议替换当前五类；全部可在 BoN 路径用现有 ledger 字段观测）：

| # | fixture | 期望行为 |
| --- | --- | --- |
| F1 | 两候选产出等价（分差 < 噪声阈值） | `basis=tie-abstain`，不得为 `verifier`；relay 双候选或回 source |
| F2 | N=2，一者超时，幸存者无 caller checks | `basis=single-candidate-unverified`；relay 明示 unverified |
| F3 | 两候选 diff 相同 / 近零距离 | 记录 `diversity≈0`，跳过 verifier，标 `no-search-space` |
| F4 | 候选无 diff、无 tool call、无 checks 通过 | 排序前淘汰；全部如此 → abstain |
| F5 | 起跑后 `POST /config` 并触发 reload | record 中的配置快照与 source 模型不变，且反映真实执行值 |
| F6 | 任一 selection 完成并 cleanup | cleanup 前 diff + 压缩轨迹 + 快照已落盘可读 |
| F7（仅 legacy 保留时） | lane 输出 `finish_reason=length` | 判 `insufficient_evidence`，不得输出 score |

当前五类中「compactTrace 丢证据」「共享错误→评分一致」「手动验证选错 turn」三项，在能否映射到具体代码之前不应占 P0 名额。

**4. 何时值得建较大评测集**：F1–F6 通过；5–10 题 pilot 复跑两次，标签（basis / abstain / evidence）稳定；pilot 上 pass@N − pass@1 > 0（否则 verifier 没有可捞回的空间，评测集测不出东西）。

## F. 目标架构

| 层 | 负责 | 不负责 | 输出 |
| --- | --- | --- | --- |
| 证据层 | 每候选 diff、tool-call 日志（稳定 ID + 显式「已丢弃区间」）、checks 输出/退出码、时序；起跑配置快照、候选模型、source 模型；**cleanup 前落盘** | 任何判断 | 不可变 evidence bundle |
| 确定性验证层 | checks（落盘脚本 + 进程组 kill）、has-work gate、diversity 距离、截断检测 | 通过者之间的优劣偏好 | `objectiveEvidence ∈ {pass, fail, none}`、`diversity`、`truncated` |
| LLM 审查层 | 仅对通过确定性层的候选做 pairwise / listwise 偏好；输出 margin 与 `agreement` | 声明事实、声明完成、写回 | `preference`、`margin`、`agreement` |
| 策略层 | 准入、N/K/P/effort、带探活的模型路由、预算、决定 relay 还是 abstain | 合并代码 | `decision ∈ {relay, abstain}`  • 理由 |
| 交付层 | relay 携带 basis 与状态；source idle 后置审计（HEAD 增量 + 测试）；审计完成后才允许 cleanup | 选 winner | `delivered ∈ {yes, no, unknown}` |

**状态词表**（只允许这样叫）：

| 状态 | 授予条件 | 不代表 |
| --- | --- | --- |
| `completed` | 管道到达终态且无错误 | 质量、交付 |
| `winner` | 被选中 relay 的候选；必须同时带 `basis ∈ {verifier-margin, objective-count, single-survivor}` 与 `objectiveEvidence` | 已验证、已交付 |
| `verified` | 仅当确定性证据 pass（checks 通过或等价可执行证据） | 由 LLM agreement 授予 |
| `delivered` | 后置审计确认 source 集成（diff 存在 + 测试通过） | 缺审计时一律 `unknown` |
| `abstain` | 见下 | 失败 |

**必须 abstain 的条件**：margin < 噪声阈值；所有候选 `objectiveEvidence=none` 且无 has-work 证据；`diversity≈0`；verifier 不可用；（可选严格模式）多幸存者且无任何 checks。

原则：不以增加模型数量解决结构性问题——上述每一层都可以在 N=2、单模型下先验收。

| 3. 最不该做的三件事 | ① 抬 8192 / 抬 effort；② 扩模型池、切 exploration、加 N/K/P；③ 建 20–30 题评测集或继续把历史搬进文档 |
| 4. 只能修一个 | **`winner` 收紧**：margin 低于噪声或无做事证据 → abstain。它同时消除错误 winner、错误叙事，并给后续所有度量一个可信锚点 |
| 5. 最可能错的现有结论 | 架构页首条「2026-09-05 有真实多幸存者 ranking 成功记录」——作为「流程曾走通」成立；作为「verifier 已可靠选优」不成立；作为「架构已证明质量提升」更不成立。两条记录的分差都落在同一文档判为不可信的区间。建议改写为：「2026-09-05 曾完成多幸存者 ranking 流程；当前没有证据证明 ranking 结果优于随机选择，也没有与客观 oracle 的一致性数据。」（二轮修订：由「结论错误」收紧为「语义过强」——事实句保留，只收紧解释。）次选：P0 五类 fixture 把 legacy 路径机制写成了 BoN 路径验收（见 0.3 二轮复核） |

**回答核心问题——当前最应该修复的，是模型能力不足，还是证据与状态语义不可靠？** 证据与状态语义。理由：即使换上完美 verifier，在现有留存与语义下也**无法被证明**有效；而现有数据已显示系统在自判不可信的分差下照常发 `verifier` winner。

### I.1 三处校正的裁决

| 校正 | 裁决 | 采纳后的口径 | 保留的分歧 / 补充 |
| --- | --- | --- | --- |
| 1. margin 阈值不能写死，须先做控制实验校准 | **采纳** | margin 低于 calibrated_noise(condition) → abstain；condition = verifier 模型 × effort × 任务规模档。实验设计见 I.4 | 校准不得成为门禁上线的前置条件：先以 fail-closed 的**临时阈值**上线（历史同模型近平局带 ≤0.026 只作下界，标 `provisional`），校准并行；每条 record 必须写入当时使用的阈值与 condition key，否则事后无法复核 |
| 2. 「必须有做事证据」不能套用所有任务 | **采纳** | 证据策略按任务类型定义（I.3）；「无工具调用」本身永不作为淘汰条件 | 任务类型必须在**准入阶段**由 caller 或确定性分类器声明并写入 ledger，不得由候选/LLM 自报；凡为候选开了 worktree 的任务默认按代码/文件类处理；纯文本任务没有确定性证据层，最高只能到 `ranked_winner(llm-only)`，**永不** `verified` |

**对评审方一处判断的反驳**：评审建议「实现时优先保证 evidence visibility」。不同意其作为单一优先级，理由见 I.6。

### I.2 winner 状态机（追问 C）

原则：一个 `winner` 字段不再承载多种含义；新增 `outcome` 字段；`winnerBasis` 保留但取值收窄；`verified` 不是状态，是只能由确定性证据授予的谓词。

候选级状态：

| 状态 | 授予条件 | 记录字段 |
| --- | --- | --- |
| `candidate_finished` | rollout 到达终态无错误 | `toolCalls`、`diffStat`、`durationMs` |
| `candidate_eliminated` | timeout / progress / checks 失败 / 任务类型最低证据缺失 | `eliminatedReason` |
| `candidate_objective_passed` | caller checks 全通过 **且** 满足 I.3 的任务类型最低证据 | `objectiveEvidence=pass` |

selection 级 outcome（互斥，恰有一个）：

| outcome | 授予条件 | relay 行为 | 禁止的解读 |
| --- | --- | --- | --- |
| `ranked_winner` | ≥2 个 objective_passed 幸存者；margin > 该 condition 的校准阈值；若做了位置对换，符号一致 | relay winner，头部带 `basis=verifier-margin`、margin、阈值 | ≠ verified；≠ 正确 |
| `objective_only_result` | ≥2 幸存者；verifier abstain 或不可用；确定性排序（测试通过数 / checks 通过数）**严格**分出先后 | relay 首位，`basis=objective-count` | ≠ verifier 选优 |
| `single_candidate_fallback` | 恰 1 个幸存者；未发生任何比较 | relay 该候选，头部明示「未经候选间比较」及其 `objectiveEvidence` | **≠ verifier 选优成功**；≠ 端到端闭环证明 |
| `insufficient_evidence` | 有幸存者，但无一满足任务类型最低证据 | 不 relay「winner」；回 source 说明「候选未产生可核验工作」 | ≠ 失败；≠ 完成 |
| `abstain` | ≥2 幸存者，margin 在噪声内或位置对换后符号翻转，且确定性排序打平 | relay 双 finalist 不带 winner 标签，或回 source | ≠ 失败 |

标志位（非状态）：`noSearchSpace`（候选 diff 距离≈0 → 去重后按 single_candidate 处理并记录）、`llmOnly`（全部候选 `objectiveEvidence=none`）。

交付级：`delivered ∈ {yes, no, unknown}`——仅由 source idle 后置审计授予（HEAD 增量非空 ∧ 测试通过 → yes；审计执行且未发现集成 → no；未执行 → unknown，**默认 unknown**）。

`verified` 谓词：只可加在 `candidate_objective_passed` 与 `delivered=yes` 上；`ranked_winner` 不因排序获得 verified；LLM agreement 永不授予 verified。`completed` 保留原义（管道终态无错误），任何报告不得单独以 completed 作为质量或交付证据。

兼容：`winnerBasis` 取值收窄为 `{verifier-margin, objective-count, single-survivor}`；读 `winnerIdx` 的消费者必须先读 `outcome`。

### I.3 任务类型证据策略（追问 B）

| 任务类型 | 最低确定性证据 | 证据缺失 → outcome | 可达最高状态 |
| --- | --- | --- | --- |
| 代码修改 | 非空 diff ∧（测试/checks 通过 ∨ 明确记录的失败） | `insufficient_evidence` | verified |
| 文件操作 | 目标路径存在性 / 内容哈希变化 + 操作退出码 | `insufficient_evidence` | verified |
| 部署 / 运维 | 命令退出码 + 服务状态探测 + 至少一次真实请求结果 | `insufficient_evidence` | verified |
| 外部事实核验 | 来源 URL 可解析 + 抓取时间 + 引用文本可在抓取内容中定位（确定性） | `insufficient_evidence` | verified（仅引用可定位性） |
| 纯文本回答 / 设计讨论 | 无确定性证据层；只检查硬约束（格式、必答项、长度） | 不适用；标 `llmOnly=true` | `ranked_winner(llm-only)`，**永不 verified** |

规则：① 任务类型在准入阶段声明并写入 ledger（caller 显式给出，或确定性分类器：是否需要 worktree、是否引用路径/文件）；② 候选/LLM 不得自报任务类型；③ 类型未知且已开 worktree → 按代码/文件类处理；④ 纯文本任务原则上不应进入需要 worktree 的 BoN 路径，若进入则全程 `llmOnly`。

### I.4 calibrated margin 最小实验（追问 D）

目标：得到每个 condition 下「无真实差异」时 margin 的分位数（q95 / q99），并确认 verifier 对已知差距的敏感度。**不允许**把 0.026 当通用阈值——它是 7 条历史记录的极差观测，不是噪声分位数。

| 组 | 构造 | 测什么 | 最小样本 |
| --- | --- | --- | --- |
| C0 同一候选 vs 同一候选 | 同一 diff / 轨迹同时作为 A 与 B | 零假设下 margin 分布（噪声）；s_A − s_B 的系统偏移 = 位置偏置 | ≥5 个 fixture × ≥10 次重复 / condition |
| C1 明显更好 vs 明显更差 | oracle 已知：一者全部测试通过，一者至少一项失败或含明显缺陷 | 敏感度：margin 高于 q95 且符号正确的比例；A/B 与 B/A 各跑一遍 | ≥5 对 × 2 顺序 × ≥3 次 |
| C2 接近但不同 | oracle 已知的小差距（如 5/5 vs 4/5 测试；同测试但一方在未覆盖分支有记录缺陷） | 分辨力下限：从哪级差距起 margin 才离开 q95 | ≥5 对 × 2 顺序 × ≥3 次 |

要点：「接近但不同」必须由 oracle 定义，不能由 verifier 自己定义；C0 若显示显著位置偏置，则所有正式比较必须做 A/B 对换，符号翻转即 abstain。

condition 分层：先只在**实际默认运行条件**（minimax-m3、effort=low、maxWorkers=1）校准；再用同一批 fixture 跑 effort=max 一次——若 q95 无显著差异则合并 condition，不要预先按每个 effort / 模型拆分。任务规模只分两档（按 ranking 输入 token 数）。在 max 档校准是浪费：默认自动路径是 low。

阈值规则：margin ≤ q95(C0；condition) → abstain（严格模式用 q99）。阈值、condition key、位置对换一致性写入每条 record。

成功标准：C0 的 q95 在两轮独立重复间相对差 < 20%；C1 在 margin 高于 q95 时符号正确率 ≥ 90%；C2 给出明确的分辨力下限。

失败后的决策：C1 符号正确率 < 70% → 该 condition 下 verifier 不能作排序信号，**不抬 effort、不换模型**，先把确定性证据摘要（测试结果、diff stat）喂进 ranking 输入再重跑 C1；若 C0 的 q95 ≥ C1 的典型 margin → verifier 无分离能力，排序改为 `objective-count` 主序、LLM 仅 tie-break。

不得同时改动：verifier 模型、N/K、策略提示词、checks。

### I.5 最小审计包与清理顺序

cleanup 前必须落盘（如 `.data/selection-artifacts/{selId}/`）：

- 起跑时**生效值**的配置快照（不是源码默认值）：strategy、models、N/K/P、effort、timeouts、provider、baseURL host
- 每候选：模型、`toolCalls`、diff（小于设定阈值存全文，否则存 stat + hash）、checks 命令 / 退出码 / 输出头部、`eliminatedReason`
- ranking 输入摘要：ranker 实际看到的文本的 hash + 长度 + 被丢弃区间
- ranking 结果：scores、margin、阈值、condition key、对换一致性、verifier 模型
- `outcome`、`winnerBasis`、`objectiveEvidence`、`llmOnly`、`noSearchSpace`
- source 模型；后置审计：HEAD before/after、diff stat、测试退出码、`delivered`

顺序：写审计包 → source 后置审计完成（或超时记 `delivered=unknown`）→ 才允许清理完整 workspace。轨迹全文不强制保存（隐私 / 磁盘），保存压缩摘要与丢弃区间即可。

### I.6 只能改一个机制：winner gate vs evidence visibility vs artifact retention（追问 F）

| 机制 | 改变什么 | 依赖 | 不改的代价 | 所属路径 |
| --- | --- | --- | --- | --- |
| winner gate（I.2 + I.3） | 系统**今天的动作**：不再 relay 无工作候选与噪声内的「verifier winner」；single-candidate 不再被叙述成选优 | has-work 部分只需现有 ledger 字段（`toolCalls`、diff、checks）；margin 部分先用临时阈值 | 继续产生错误 winner 与错误叙事（已发生：cd6590de；用户侧读数：最新记录 single-candidate、nComparisons=0、toolCalls=0） | BoN（`src/selection/`） |
| evidence visibility（compactTrace ↔ citation audit） | legacy verifier **报告**的引用完整性：finding 不得引用被丢弃的证据 | 源码位置（用户侧已确认在 `src/index.ts`） | 手动 / legacy 核验报告可能给出虚假 supported；但按 I.2，LLM finding 本就不能授予 verified，不污染状态机 | legacy（`src/index.ts`） |
| artifact retention（I.5） | 可归因性与可校准性 | 无 | 无法校准阈值、无法做事后 oracle；但**不改变任何动作** | 两者 |

**单一优先级：winner gate。** 三者中只有它改变系统今天输出什么；它不等校准完成（fail-closed 临时阈值），也不等留存（字段已在 ledger）。评审方的依赖论证「verifier 引用看不见的证据 → winner gate 无基础」不成立：I.2 / I.3 下 winner gate 的输入全部是确定性字段，不经过任何 LLM finding；citation audit 修的是 legacy 报告的引用完整性，且 LLM finding 不能授予 verified，其错误的传播范围被状态机截断。它升级为同级的**唯一条件**：`/verify` 报告被用于人工判定交付是否可信——若是，先在报告头部加「引用未审计」标记，成本更低。retention 排第二，因为校准（I.4）与 `delivered`（G-4）都依赖它。

BoN 侧也有一个「可见性」问题，但性质不同：ranking 输入若同样经有界尾部压缩（H-0905 §7.2 的 20/20），ranker 可能看不到中段的测试执行；修法不是 citation audit，而是把确定性证据摘要（checks 结果、diff stat、toolCalls）作为结构化字段前置进 ranking 输入。是否与 legacy 共用 `compactTrace()`：**源码裁决——不共用**；ranking 输入走 `renderTrajectory()`（24000 字符、头部截断、保留尾部），checks 结果与 diff 均不进入输入（J.1-12）。

### I.7 修订后的两周顺序（合并评审方 6 步与本页 G）

1. **状态机 + winner gate**（合为一次改动；I.2 / I.3；临时阈值标 provisional）——评审方第 1、3 步合并
2. **审计包 + 配置快照 + 清理顺序**（I.5）——评审方第 4 步前移，因为第 3 步依赖它
3. **校准实验 C0 / C1 / C2**（I.4）——即评审方第 5 步的「3 个控制 fixture」，输出正式阈值替换临时值
4. **source 后置审计 → `delivered`**（G-4）——评审方未单列，但其「最大盲区」一段正是此项
5. **legacy evidence visibility 契约**：`compactTrace()` 返回 `{text, visibleEvidenceIds, droppedRanges}`；`auditFindingCitation()` 只接受 `visibleEvidenceIds`，越界引用 → finding 降为 `insufficient_evidence`、reason=`cites_dropped_evidence`；`traceFor()` 在压缩前分配稳定 ID；验收 fixture：关键工具结果位于被丢弃的中段、finding 引用之 → 期望被拒——评审方第 2 步后移；若 `/verify` 被用于交付判定则提前到第 2 位
6. 之后才是：采样多样性单变量实验（G-5）→ 小规模代码题集 → 最后 8192 / effort / 模型池 / N/K/P / exploration

与评审方的差别只有两处：evidence visibility 从第 2 位移到第 5 位（理由见 I.6）；retention 从第 4 位移到第 2 位（校准依赖它）。
